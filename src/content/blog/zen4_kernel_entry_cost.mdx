My [last post](/blog/audit_rules_disk_throughput/) ended on a reassuring line: "The older nodes are still somewhat slower than the newer ones: that part really is hardware."

That line also hid a problem.

Once the audit rules were gone, I re-ran the Postgres benchmark. The older nodes (AMD EPYC 9654, Zen 4) were still about **2× slower** than the newer ones (EPYC 9655 and 9755, Zen 5). Meanwhile sysbench's CPU test said the gap should be **1.15×**. A generation of CPU design and a few hundred MHz of clock can explain 15 or 30 percent. They can't explain 100.

So either Postgres was doing something odd, or "older hardware" was hiding a cost that sysbench doesn't measure.

## Benchmarking what we actually run

Synthetic benchmarks had already lied to me once, so this time I ran our own software. I used the same image versions we run in production, in one 4-CPU pod with guaranteed CPU per node, on 3 Zen 4 and 4 Zen 5 staging nodes, all in parallel:

So "the old nodes are N× slower" has no single N. It ranges from no difference at all to more than 3×, depending on the software.

There is a pattern, though: **the more time a workload spends in the kernel, the bigger the gap.** Elasticsearch and the Django HTML page barely enter the kernel and lose 20–40%. Postgres spends about half its time there and loses 2×. Redis, with one command per round trip, is almost entirely syscalls (network read, network write, poll) and loses 3.2×.

The two exceptions say the same thing in their own way. etcd is limited by disk syncs, which are equally slow on both tiers, so the CPU doesn't matter. NumPy matrix multiplication (×2.0, not in the table) never enters the kernel: its gap comes from Zen 5's full-width 512-bit vector units, which is a separate story.

## Is the old CPU just doing more work?

That was my first question, and I asked Claude to check it: maybe the Zen 4 nodes make more context switches or more system calls per operation. A different scheduler setting or kernel tunable could do that, and then the fix would be a config change.

We counted them with `perf stat` software counters, per operation:

Each cell reads Zen 4 vs Zen 5. The numbers are almost identical: both tiers do exactly the same work. The Zen 4 nodes just pay **2 to 3 times more CPU time for it**. For Postgres, that works out to about 7.9 µs of CPU per syscall against 3.5 µs.

So the question became: why is entering the kernel so much more expensive on Zen 4?

## Ruling out the usual suspects

Before blaming the CPU itself, I ruled out the rest with measurements:

- **Clock speed.** I first got 2.8 GHz on Zen 4 from the pod's counters, which looked like a power or frequency problem. It wasn't. Those counters undercount on syscall-heavy loads. The whole-node APERF/MPERF counters showed 3.4–3.6 GHz, the chip's rated all-core boost, at 281–293 W, under its 360 W limit. The Zen 5 nodes run at 4.1–4.3 GHz. That's a real 1.15–1.23× gap, and there is nothing to tune.
- **Disks, RAM, NUMA, huge pages, cpufreq governor.** Same disk reads per transaction, same memory latency (133–170 ns against 144–160 ns), same governor and boost settings. No difference worth keeping.
- **A weaker branch predictor.** On pure computation like 7-Zip, the user-space branch-miss rate is the same on both (12.7% against 12.5%). The predictor is fine.

What remained was the kernel.

## The kernel signature

`perf stat` can split cycles, instructions and branch misses between user space and kernel. This is where the two tiers stop looking alike:

On Zen 4, the kernel mispredicts **10–13% of its branches, whatever the workload**. That holds even for SHA-256 hashing, which spends 1% of its time in the kernel. On Zen 5 the rate is 0.3–1.4%. A miss rate that doesn't depend on the work being done points to something applied to every kernel code path.

The likely candidate is the mitigation for **SRSO** (Speculative Return Stack Overflow, also called Inception, CVE-2023-20569). It affects Zen 3 and Zen 4. To protect against it, Linux's default mitigation on those CPUs ("Safe RET") sends every function return in the kernel through a special return thunk, built so that the return predictor can't be steered by an attacker. Return prediction is exactly what makes deep call chains cheap. Take it away and you get mispredictions on kernel returns, which is the kind of constant, workload-independent miss rate we see. Zen 5 isn't affected, so it doesn't need the mitigation.

There's also a knock-on effect: after each trip into the kernel, user code on Zen 4 mispredicts more too (Postgres: 5.4% user branch misses against 1.4%). Each crossing seems to leave the predictor state behind it degraded.

Put the pieces together and the numbers add up:

```
Postgres TPC-B:  ×1.2 clock  ×  ×1.3 core  ×  ×1.4 kernel      ≈ ×2.2   (measured ×2.1)
Redis:           ×1.2 clock  ×  ×1.0–1.2   ×  ×2.3–2.6 kernel  ≈ ×3.1   (measured ×3.2)
```

**A caveat I want to be clear about:** this is an inference, not a proof. The clean experiment would be to boot a Zen 4 node with `spec_rstack_overflow=off` and re-run the benchmarks. We didn't, and won't: these nodes run real workloads, and turning off a security mitigation to win an argument is not a trade I want to make. What we have is a signature consistent with SRSO and nothing else that explains it.

Public benchmarks agree with that, with a nuance. When the mitigation came out, [Phoronix found](https://www.phoronix.com/review/amd-inception-benchmarks) small changes on a Zen 4 desktop CPU, and only for I/O-heavy workloads. Their later Zen 4/Zen 5 comparison found that [disabling mitigations brings no real-world benefit on Zen 5](https://www.phoronix.com/review/amd-zen5-mitigations-off/5), since it isn't affected. Typical desktop benchmarks barely touch the kernel. On our own workloads that barely touch it either (Elasticsearch, ClickHouse, Django pages), the gap is also just clock plus core: 1.2–1.4×. It's only when a service lives in syscalls that the cost shows up, and then it shows up big.

## What we can do about it

Not much on the machines:

- **The mitigation stays on.** That decision was made before I started.
- **The clock is already at its maximum** under the power limit.
- **A BIOS update with newer microcode** would bring security fixes, not speed.

So the response is about placing workloads, not tuning machines:

- **Large Postgres databases and busy Redis instances go on Zen 5 nodes.** A Postgres instance sized for 10 cores on Zen 5 needs about 20 on Zen 4.
- **Elasticsearch, ClickHouse, Python services and etcd can stay** on the older nodes, at a known 1.0–1.5× cost.
- **Making fewer syscalls per operation narrows the gap.** Pipelining, batching and connection pooling help: Redis pipelined by 16 loses 2.2× instead of 3.2×.
- **The real fix is replacing the older nodes.** This gives us the numbers to plan it with.

## How it went with Claude

Same setup as last time: Claude, Anthropic's coding agent, in my terminal, with read-only access to the clusters. I created the benchmark pods myself when it handed me the commands.

**The two questions that moved the investigation were mine.** "Benchmark everything we actually run" turned one Postgres anomaly into a pattern across a dozen workloads. "Could it be different context switching?" turned "the kernel is slower" into a measured "same syscalls, three times the price". Claude's part was turning each question into a harness. It wrote the pods with a perf sidecar for each workload, ran them on 7 nodes in parallel, and summarised the results as per-tier medians.

**It made mistakes, and the data caught them.** It first reported a 2.8 GHz clock from pod-level counters and built a power-capping theory on it. It dropped the theory once whole-node counters said 3.5 GHz. Its benchmark harness also hung twice: a shell `wait` that waited on a background server forever, and a RabbitMQ readiness check that ran only once. Both were fixed quickly, but a script you didn't read is a script you don't fully trust.

**It was careful about its own claim.** Its summary labelled SRSO as "effect measured, cause inferred". It also said what the decisive test would be and why we weren't running it, instead of presenting the inference as settled.

## What I take away from this

**"Older hardware" is not one number.** The same two machines are 1.0× or 3.2× apart depending on what runs on them. Measure your own workloads, or at least your heaviest one, before deciding where things go.

**Synthetic CPU benchmarks don't measure the kernel.** sysbench, 7-Zip and SHA-256 all said 1.15×, because none of them make syscalls. Databases and caches mostly do.

**Count the work before timing it.** Counting syscalls and context switches per operation separates "the machine does more" from "the machine pays more per unit". That split decided whether there was a config fix or not.

**Security costs are real, and sometimes you pay them in hardware.** Keeping a mitigation on can be the right call. The useful part is knowing its price per workload, so you can buy your way around it on purpose instead of by accident.
